UK Online Retail Dashboard — DAX Measures
==========================================

Create a table called _Measures first (Home ribbon > Calculations > New table).
Note the leading underscore: Power BI reserves the exact name "Measures" for
its own internal system table and will reject it if you try to name a table
that yourself.

_Measures = { "Measure holder" }

Then add every measure below to that table (Home ribbon > Calculations >
New measure, with _Measures selected in the Fields pane so they land in the
right table).

All measures below were checked against the CSVs in outputs/query_results/
(exported from the SQL views) before being written up here — e.g. Net Sales
should equal £8,465,533.16, the same figure in
outputs/query_results/02_overall_kpis.csv.

KNOWN ISSUES IN THESE MEASURES
------------------------------

FIXED - Cancellation Rate. It used to divide a numerator counted from the raw
table by a denominator counted from vw_valid_sales, after rows with no
customer ID had been removed. Two different populations, which inflated the
rate to 17.15% against a true 14.81%. It also could not be filtered:
vw_valid_sales was related to DateTable and vw_cancellations was not, so a
date filter shrank the denominator and left the numerator whole - February
2011 returned 79% against a true 15.72%.

Both faults are now fixed at the data layer. vw_all_invoices (see
sql/03_clean_views.sql) is one row per invoice for the whole dataset, cancelled
or not, each carrying a date. Both halves of the fraction are counted from it,
so the rate is consistent AND filters correctly by month.

FIXED - Net Sales was not net of returns. vw_valid_sales excludes
cancellation lines but does not subtract the original orders they reverse, so
a fully cancelled order was still counted as revenue: GBP 445,875 (5.00%),
GBP 8,911,407.90 against a true GBP 8,465,533.16.

The fix is at the data layer. vw_valid_sales_net (sql/03_clean_views.sql)
removes every sale line that a later cancellation reverses. In Power BI,
point the table named vw_valid_sales at the vw_valid_sales_net view (Transform
data > select the table > Source step > change the view in the Navigation
step) and keep the table NAME unchanged, so every measure below keeps working
and only the numbers move. Then Refresh.

What is still not removed: cancellations that carry a customer ID but match no
sale exactly. Including them would take the overstatement to GBP 611,342, so
true net sales for identified customers lies between GBP 8,300,066 and
GBP 8,465,533. The headline uses the lower correction because every line of it
can be listed and checked.

----------------------------------------------------------------------------
Net Sales =
SUM(vw_valid_sales[sales_value])

What it calculates: total revenue from genuine completed sales.
Why SUM: sales_value is already a per-line amount (quantity * unit_price),
so this is a plain additive total — no need for CALCULATE or DISTINCTCOUNT.

----------------------------------------------------------------------------
Total Orders =
DISTINCTCOUNT(vw_valid_sales[invoice_no])

What it calculates: how many separate orders were placed.
Why DISTINCTCOUNT: vw_valid_sales has one row per product line, so an order
with 5 products appears as 5 rows. Counting rows would overcount orders;
DISTINCTCOUNT collapses each invoice_no down to one, regardless of how many
lines it has.

----------------------------------------------------------------------------
Unique Customers =
DISTINCTCOUNT(vw_valid_sales[customer_id])

What it calculates: how many distinct customers bought something in the
current filter context.
Why DISTINCTCOUNT: same reasoning as Total Orders — one customer can appear
on many rows, and this needs the count of unique people, not rows.

----------------------------------------------------------------------------
Average Order Value =
DIVIDE([Net Sales], [Total Orders], 0)

What it calculates: average amount spent per order.
Why DIVIDE: DIVIDE is a safe division — if [Total Orders] is 0 (e.g. an
empty slicer selection), a plain "/" would throw a divide-by-zero error and
break the visual; DIVIDE returns the third argument (0) instead.

----------------------------------------------------------------------------
Total Items Sold =
SUM(vw_valid_sales[quantity])

What it calculates: total units sold across all valid sales lines.
Why SUM: quantity is already a per-line count, so this is a direct additive
total, same logic as Net Sales.

----------------------------------------------------------------------------
Cancelled Value =
SUM(vw_cancellations[cancellation_value])

What it calculates: the total value of cancelled orders (invoices starting
with C), kept as a positive number via ABS() in the SQL view.
Why SUM: cancellation_value is a per-line amount, same as sales_value.

----------------------------------------------------------------------------
Total Invoices =
DISTINCTCOUNT(vw_all_invoices[invoice_no])

What it calculates: every invoice raised in the period, cancellations included.
Why it exists: this is the denominator the cancellation rate always needed - a
count of the whole invoice population from one source, rather than a count of
surviving orders from a filtered view.

----------------------------------------------------------------------------
Cancelled Invoices =
CALCULATE(
    DISTINCTCOUNT(vw_all_invoices[invoice_no]),
    vw_all_invoices[is_cancellation] = TRUE
)

What it calculates: how many of those invoices were cancellations. Returns
3,836, the same as counting vw_cancellations directly.
Why count it from vw_all_invoices instead: so the numerator and the denominator
of Cancellation Rate come from the same table, on the same date relationship.
Counting one from here and the other from elsewhere is exactly the bug this
replaced.

----------------------------------------------------------------------------
Cancellation Rate =
DIVIDE(
    [Cancelled Invoices],
    [Total Invoices],
    0
)

What it calculates: cancelled invoices as a share of all invoices raised.
Format as a percentage in Power BI. Returns 14.81% for the full period.
Why DIVIDE: returns the third argument instead of erroring if the denominator
is 0 - which happens the moment a slicer excludes everything.
Why this is now correct: both measures read from vw_all_invoices, which is one
row per invoice for the entire dataset and is related to DateTable. Filter to
February 2011 and it returns 15.72%, which is the real February rate. The old
version returned 79%.

Check against outputs/query_results/59_cancellation_rate_corrected.csv (full
period) and 60_cancellation_rate_by_month.csv (monthly).

----------------------------------------------------------------------------
High-Value Active Customers =
CALCULATE(
    COUNTROWS(vw_customer_profile),
    vw_customer_profile[customer_segment] = "High-value active"
)

What it calculates: number of customers who are both high-spend and recently
active (the two decisions a Sales Manager cares about most: who is valuable,
and are they still buying).
Why CALCULATE: vw_customer_profile has one row per customer already, so
COUNTROWS gives a customer count directly, but it needs to be counted only
within the "High-value active" segment — CALCULATE overrides the filter
context to apply that condition regardless of what else is sliced on the
page.

----------------------------------------------------------------------------
High-Value At-Risk Customers =
CALCULATE(
    COUNTROWS(vw_customer_profile),
    vw_customer_profile[customer_segment] = "High-value at risk"
)

What it calculates: high-spend customers who haven't ordered in over 90 days
relative to the dataset's last transaction — the retention priority list.
Why CALCULATE: same reasoning as High-Value Active Customers, filtered to a
different segment value.

----------------------------------------------------------------------------
At-Risk Repeat Customers =
CALCULATE(
    COUNTROWS(vw_customer_profile),
    vw_customer_profile[customer_segment] = "At-risk repeat customer"
)

What it calculates: repeat customers (2+ orders) below the £1,000 high-value
threshold who have also gone quiet for 90+ days.
Why CALCULATE: same pattern again, filtered to the "At-risk repeat customer"
segment.

----------------------------------------------------------------------------
Active Repeat Customers =
CALCULATE(
    COUNTROWS(vw_customer_profile),
    vw_customer_profile[customer_segment] = "Active repeat customer"
)

What it calculates: repeat customers (2+ orders) below the GBP 1,000 high-value
threshold who HAVE ordered within the last 90 days - the healthy middle of the
customer base.
Why CALCULATE: same pattern as the other segment measures.
Why it matters that this one exists: there are five segments. Without this
measure the Page 2 KPI row only accounts for 3,477 of 4,327 customers, and the
850 customers in this segment silently vanish from the page.

----------------------------------------------------------------------------
One-Time Customers =
CALCULATE(
    COUNTROWS(vw_customer_profile),
    vw_customer_profile[customer_segment] = "One-time customer"
)

What it calculates: customers who have only ever placed a single order.
Why CALCULATE: follows the exact same CALCULATE + COUNTROWS pattern as the
other three segment measures, so all four KPI cards on Page 2 are built the
same way.
